**odjson** — *overdrive JSON* — は、`encoding/json/v2` を **外側から** JIT コンパイルされたサードパーティコーデック並みに速くする CLI コードジェネレータ。差し替えるのではなく、後付けする。標準ライブラリはそのまま、呼び出し側は一箇所も書き換えず、生成されたファイルを 1 つ消せば全部なかったことになる。

```go
//go:generate go tool odjson -type User
```

```sh
$ go generate ./...     # odjson_gen.go を書き出す
$ rm odjson_gen.go      # そして、アンインストールはこれで全部
```

**`encoding/json/v2` に対して 2.1×〜3.6×** — 4 つの測定すべてで。[`goccy/go-json`](https://github.com/goccy/go-json) にはすべての測定で先行し、[`bytedance/sonic`](https://github.com/bytedance/sonic) の JIT コンパイルされた SIMD コーデックとは 3 つで互角、small のデコードでは 1.7× 先行する。それでいて中身は標準ライブラリのままで、ビルドにサードパーティのコーデックは入らない。（ただしモジュールが 1 つだけ付いてくる: 生成ファイルはランタイムサポートパッケージ `github.com/mazrean/odjson/odjsonrt` を import する — [動作要件](#動作要件)を参照。）

ペイロードは sonic 自身のフィクスチャで、名前も sonic の付けたものに従う。`large`（616 KiB、深くネストし `interface{}` フィールドだらけ — sonic の `twitter.json`。[`bench/`](./bench) と [docs/internals.md](./docs/internals.md) では今も `twitter` と呼んでいる）と `small`（340 B、完全に型付けされた、呼び出しごとのオーバーヘッドを見るケース）。ベースラインの棒と odjson の棒の違いは、生成ファイルの有無だけ。

<details>
<summary>数値の読み方と、再現の仕方</summary>

ベンチマークスイートは [`bench/`](./bench) モジュールにある。`sonic` や `goccy/go-json` をはじめとする比較対象のライブラリが `github.com/mazrean/odjson` の依存にならないよう、独立したモジュールにしてある。

```sh
cd bench
go test -bench . -benchmem ./...
```

- 主役は 2 つの標準ライブラリで、`sonic` と `go-json` はものさし。odjson はこの 2 つを速くはしない（[理由と測定値](./docs/internals.md#the-two-third-party-libraries)）ので、それぞれ自前の速度で並んでいるだけ。
- `sonic.Marshal` のデフォルト設定は HTML エスケープも UTF-8 検証もしないので、そのエンコードの棒は同じ仕事をしていない。両方を行う `sonic.ConfigStd` は 126 µs と 367 ns。
- チャートの数値は別々の 2 つのプロセスから取ったもの。絶対値としては問題ないが、生成ありの行とそのベースラインのあいだの小さな差を見るには向かない。それには両側を 1 プロセス内で測る `bench/ab` を使う。sonic の 4 行のうち 3 行はチャートの 4% 以内に収まり、`small` のエンコードは 12% 低く出る。sonic 自身の `large` デコードは実行ごとに 480〜550 µs のあいだで揺れている。
- `encoding/json` v1 も速くなる — 4 つのうち 3 つで 1.2×〜1.6×、`large` のエンコードでは 4% 遅い。その行は[測定結果の表](./docs/internals.md#the-measured-tables)にある。`json/v2` の話を読みやすく保つため、チャートからは外してある。

要点は odjson が全ての行で勝つことではない。中身は標準ライブラリのままで、サードパーティのコーデックはなく、呼び出し側は変わらず、戻すにはファイルを 1 つ消すだけ、というところにある。マイクロ秒がどこへ消えているか、何を試して却下したか、なぜ sonic と go-json は速くできないのか — 全ての勘定は [docs/internals.md](./docs/internals.md) にある。

</details>

> [!IMPORTANT]
> 採用する前に確認すべきことが 2 つある。どちらもこの下に書いてある。コーデックを生成すると[既存の呼び出し側が出力する JSON が変わる](#出力される-json-が変わる)こと、そして上の速度は[標準ライブラリの内部実装に依存している](#標準ライブラリの内部実装に依存している)こと。

## 動作要件

- **Go 1.27 以降。** odjson は `encoding/json/v2` 向けに生成する。これは Go 1.27 で標準ライブラリに入り、そこではデフォルトで有効になっている。生成ファイルは `encoding/json/jsontext` を import するので、Go 1.26 以前ではコンパイルできない。1.27 以降は `encoding/json` 自体が `encoding/json/v2` の上に実装されている — 変更していない v1 の呼び出し側が生成された v2 のメソッドに届くのはそのためであり、[出力される JSON が変わる](#出力される-json-が変わる)のも同じ理由。
- **モジュールが 1 つビルドに加わる**: 生成ファイルはランタイムサポートパッケージ `github.com/mazrean/odjson/odjsonrt` を import する。CLI と同じモジュールに入っているので、`go get -tool` が一緒に追加してくれる。サードパーティの JSON コーデックは関わらない。
- **追加のビルド手順はない。** `odjson_gen.go` はビルドタグのない普通の Go コードで、`// Code generated by odjson. DO NOT EDIT.` ヘッダを持ち、リポジトリにコミットする。ツールを入れていない開発者も普通にビルドでき、odjson が要るのは再生成するときだけ。

## クイックスタート

ジェネレータはプロジェクトのツールとして入れる。そうすれば全員が — CI も — 同じバージョンで生成する。

```sh
go get -tool github.com/mazrean/odjson@latest
```

速くしたい struct の隣に `go:generate` 行を置く。

```go
package model

//go:generate go tool odjson -type User,Post

type User struct {
	ID    int64  `json:"id"`
	Name  string `json:"name"`
	Email string `json:"email,omitempty"`
}
```

そして、

```sh
go generate ./...
```

odjson はソースの隣に `odjson_gen.go` を書き出す。中身は各型のコーデック。コミットしておく。ビルドタグの要らない普通の Go コード。

統合作業はこれで全部。呼び出し側はそのまま。

```go
func handler(w http.ResponseWriter, r *http.Request) {
	var u model.User
	if err := json.Unmarshal(body, &u); err != nil {
		// ...
	}

	b, err := json.Marshal(&u)
	// ...
}
```

外すときは `odjson_gen.go` を消して、ビルドし直すだけ。

### フラグ

```
odjson [flags] [packages]
```

パッケージ引数を渡さない場合、odjson はカレントディレクトリのパッケージに対して生成する。`//go:generate` が必要とするのはこの挙動。

| フラグ              | デフォルト        | 説明                                                                                                          |
| ------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------- |
| `-type`             | 全て             | struct 型名のカンマ区切り。デフォルトはパッケージ内で宣言された全てのエクスポートされた struct。                    |
| `-output`           | `odjson_gen.go`  | 一致した各パッケージのディレクトリに書き出すファイル名。パスではなく、名前。                                        |
| `-recursive`        | `true`           | 選択した型から到達できる struct 型のコーデックも生成し、ネストした値もリフレクションを回避する。                     |
| `-escape-html`      | `true`           | 文字列中の `<`、`>`、`&` をエスケープする。`encoding/json` のデフォルトに合わせた挙動。                            |
| `-case-insensitive` | `false`          | `UnmarshalJSON` で、`encoding/json` v1 と同じく大文字小文字を無視したメンバ一致にフォールバックする。デフォルトは無効で、`encoding/json/v2` に合わせてある。 |
| `-version`          |                  | バージョンを表示して終了する。                                                                                   |

## 導入すると何が変わるか

生成ファイルをコミットすると、2 つのことが変わる。どちらも odjson が隠しているものではないし、どちらも導入前に読んでおく価値がある。

### 出力される JSON が変わる

呼び出し側は書き換えないが、そこから出てくるバイト列は動く。Go 1.27 以降、`encoding/json` は `encoding/json/v2` の上に実装されていて、`json/v2` は型が両方を提供している場合 `MarshalJSONTo` を優先する。つまり生成済みの型では、変更していない `json.Marshal` / `json.Unmarshal` が `encoding/json/v2` のセマンティクスを得る。`encoding/json` 自身のオプションが v1 のものを戻す箇所を除いて。

同じ型を 2 回宣言し — 片方は生成ファイルあり、もう片方はなし — で測った、普通の `encoding/json` 呼び出し側の前後の違いがこれ。

| `encoding/json` の呼び出し側での挙動 | odjson なし | odjson あり |
| --- | --- | --- |
| nil の slice / map | `null` | `[]` / `{}` |
| nil の `[]byte` | `null` | `""` |
| `0` や `false` に対する `omitempty` | 省略される | **保持される** |
| scalar、struct、`time.Time`、`,string` フィールドへの `null`（デコード） | 触られない | **ゼロ値になる** |
| 配列の長さの不一致（デコード） | 詰められるか切り詰められる | **拒否される** |
| 大文字小文字の違うメンバ名（デコード） | 一致する | **一致しない** |
| map のメンバ順 | 名前順 | 名前順 — *変わらない* |
| `<`、`>`、`&`、U+2028/9 | エスケープされる | エスケープされる — *変わらない* |

> [!WARNING]
> まず確認すべきはデコードの 3 行。今日サービスが受け付けている入力が **拒否される** ようになったり、これまで触っていなかったフィールドを **ゼロ値にする** ようになったりし得る。最後の 1 行は `-case-insensitive` では戻らない。このフラグは、そして `-escape-html` も、v1 の `UnmarshalJSON` / `MarshalJSON` メソッドにしか届かず、`json/v2` の呼び出し側はそれらを一度も通らない。

一番心配される 2 行は **変わらない**。生成されたエンコーダは `encoding/json` と同じく map のメンバを名前順に並べるので、map を含む struct はバイト単位で安定したまま。ゴールデンファイル、文字列比較のテスト出力、シリアライズしたボディへの署名は、どれもそのまま動く。そして `encoding/json` はマーシャラが返したものに自前の HTML エスケープをかけるので、v1 の呼び出し側では `<`、`>`、`&`、U+2028/9 はエスケープされたまま。（`json/v2.Marshal` を直接呼ぶとエスケープされないが、それは `json/v2` のルールであって odjson が持ち込んだものではない。）

この背後にあるメソッドごとのルールは、`GOEXPERIMENT=nojsonv2` ビルドで何が見えるかも含めて [docs/internals.md](./docs/internals.md#which-semantics-a-generated-method-follows) にある。特に効いてくるのはライブラリを公開する場合。生成されたメソッドはあなたの型のエクスポートされた API であり、利用者はそれを継承する。だから後からファイルを消すのは、彼らにとってはきれいなアンインストールではなく破壊的変更になる。

> [!WARNING]
> **埋め込みについて。** 生成済みの型を埋め込みながら自分自身のコーデックを持たない struct は、埋め込んだ型のメソッドを継承してしまい、**その埋め込み部分だけ** としてエンコードされる — 自分のフィールドを黙って落として。パッケージ内であればデフォルトがこれをカバーする。エクスポートされた全ての struct と、`-recursive` が到達する全てが対象になるから。注意すべきなのは `-type` で絞った場合と、**別のモジュールがあなたの生成済みの型を埋め込みながら** 自分のパッケージに odjson をかけていない場合。後者が起きても手元には何のシグナルも出ない。つまり、エクスポートする型は、それを埋め込む側にもコーデックが要る型ということ。

### 標準ライブラリの内部実装に依存している

上の `json/v2` の速度は、生成されたコードだけから出ているのではない。標準ライブラリのエクスポートされた面の外側に踏み出す **直接パス**（`odjsonrt/direct.go`）から出ている。バッファ付きでオプションのない素の `json.Marshal` / `json.Unmarshal` のトップレベルの値に対して、odjson は `jsontext` の公開 API を通さず、`reflect` で計算したフィールドオフセットと `unsafe` を使って `encoding/json/v2` のコーダ自身のバッファに直接書き、そこから直接読む。そうしているのは、`json/v2` 自身のコーデックが同じ状態に internal な export 経由で到達していて、リンカが他のモジュールにそれを使わせないから。そして公開 API は固定費とメンバごとの重複名チェックを課し、それがあの数値を届かないところに追いやるから。

**これはどんな互換性保証もカバーしない、エクスポートされていない標準ライブラリのレイアウトへの依存。** 失われるものが速度だけで済むよう、柵で囲ってある。

- **一度に 1 つの Go マイナーバージョンに対してのみ検証され**（現在は 1.27）、そのバージョンでゲートされる
- **init で型によって検査され**、さらに **init で自己テストされる**。直接パスを `json/v2` 経由で走らせ、末尾の余分なデータの拒否も含めて、公開 API と答えを突き合わせる
- **どこかで失敗すればプロセス全体で無効化され**、結果は `odjsonrt.DirectEnabled` が報告する。知らせてほしければテストでアサートすればいい
- **`-tags odjson_safe` で丸ごとコンパイルから外れる**
- **生成された全てのメソッドが公開 API のパスをフォールバックとして持ち**、ネストした値、`io.Writer` / `io.Reader`、オプション付き、そして全ての `encoding/json` 呼び出しでは、そちらを通る

> [!IMPORTANT]
> **新しい Go リリースで何を払うことになるか。** Go 1.28 が出たとき、odjson は検証していないレイアウトを信用しない。直接パスは 1.28 対応を入れたリリースが出るまで無効のままで、それまで生成済みの型は完全に公開 API のパスで動く。あなたのコードはコンパイルでき、同じ JSON を出し続ける — ただし上の `json/v2` の数値は直接パスのものであり、それがないと標準ライブラリに対する差は大きく縮まる。エンコード側に至っては、もう勝ちですらなくなる。Go のアップグレードに合わせてバージョンを上げる計画を立てるか、そもそもこれに依存したくないなら `-tags odjson_safe` でビルドする。リリースを監視して、そのバージョンでもレイアウトが通ることを確かめたうえでプルリクエストを開く nightly のワークフローがある — だから待つのはレビューとタグであって、発見ではない。両方のパスの測定値は [docs/internals.md](./docs/internals.md#the-direct-path) にある。

## 仕組み

Go の struct は、その JSON の形について必要なことをコンパイル時に既に全部語っている。ランタイムのライブラリはそれを捨てて、呼び出しのたびにリフレクションで再発見する。odjson は struct 定義を前もって読み、それぞれについてリフレクションのない専用コードを書き出す。

### 標準ライブラリに後付けする

odjson は `encoding/json/v2` を置き換えない。型 `T` ごとに、標準のマーシャリングインターフェース 4 つと、その背後にあるエクスポートされていないコーデックだけを出力する。

| シンボル                                        | インターフェース                                            |
| ---------------------------------------------- | ---------------------------------------------------------- |
| `(T).MarshalJSONTo` / `(*T).UnmarshalJSONFrom` | [`encoding/json/v2`](https://pkg.go.dev/encoding/json/v2) のストリーミングインターフェース。Go 1.27 で `json.Marshal` が届く先であり、速さがあるのもここ。 |
| `(T).MarshalJSON` / `(*T).UnmarshalJSON`       | [`encoding/json`](https://pkg.go.dev/encoding/json) v1 のインターフェース。v1 のルールに従う。 |

生成される API の面は、これで **全部**。呼ぶべき odjson のシンボルもなければ、ラッパー型も設定オブジェクトもない。あなたのプログラムのどこにも odjson は現れない。既に書いてある `json.Marshal(v)` と `json.Unmarshal(b, &v)` の全てが、生成されたコードにディスパッチする。

そこから 2 つの帰結が出てきて、それが売りの全部。

- **標準ライブラリのままでいられる。** そのオプションも、エラー型も、ストリーミングデコーダも、それらの型に触れるプログラム内の他の全ても、そのまま動く。odjson はライブラリが元から探していた 2 つのメソッドを供給するだけだから。
- **いつでも外せる。** `rm odjson_gen.go` してビルドし直せば、パッケージは素のリフレクションに戻る。巻き戻すべき移行作業も、解くべき API もない。だから試すのが安く、将来の標準ライブラリが差を埋めたときに捨てるのも安い。（[導入すると何が変わるか](#出力される-json-が変わる)に 1 つだけ注意書きがある。型を *公開している* 場合、生成されたメソッドは利用者が継承するエクスポート API なので、ファイルを消すのは彼らにとって破壊的変更になる。）

### 生成されたコードがすること

- **Marshal** — 生成コードは struct のフィールドをバイトスライスに直接 append する。フィールド名、クォート、区切り文字は定数として生成ソースに焼き込まれている。（[`sapphi-red/json-constantiater`](https://github.com/sapphi-red/json-constantiater) と同じ発想。）
- **Unmarshal** — 生成コードはその struct 専用のパーサ。入力を struct のフィールドへ直接流し込む。リフレクションなし、中間の `map[string]any` なし、実行時のフィールド名ルックアップなし。メンバ名はクォートごとドキュメントの生バイトと突き合わせ、bool、整数、単純な float はその場でデコードする。高速パスが見通せないものは、推測せず汎用パーサへ落ちる。
- **どのデコーダが走るか** は値ごとに実行時に決まる。適用できるなら直接パス、小さい値には値全体を読むバイトパーサ、大きい値には `jsontext.Decoder` をトークン単位で駆動するパス。最後のものがストリーミングデコードのメモリを抑える。

既に `json.Marshaler`、`json.Unmarshaler`、`encoding.TextMarshaler`、`encoding.TextUnmarshaler` を実装している型はそのまま。odjson は衝突するメソッドを生成せず、既存のメソッドを呼ぶ。

## 正しさ

odjson の契約はインターフェースごとに 2 つに分かれている。`MarshalJSON` / `UnmarshalJSON` は同じ型に対する `encoding/json` v1 と完全に同じ挙動をし、`MarshalJSONTo` / `UnmarshalJSONFrom` は `encoding/json/v2` と完全に同じ挙動をする。どちらの半分も、主張ではなくフィクスチャで担保されている。

- **パリティフィクスチャ** が `internal/testfixture/` にあり、ジェネレータが知っている全てのフィールド形状をカバーする。あらゆる数値幅、`[]byte` と `[N]byte`、ポインタ、slice、配列、map、`any`、`json.RawMessage`、`json.Number`、`time.Time`、値による埋め込みとポインタによる埋め込み、`omitempty`、`omitzero`、`,string`、`-`、エクスポートされていないフィールド、自己参照型とパッケージをまたぐ型、ジェネリクス、その他のフォールバック — それらを標準ライブラリと **バイト単位で** 比較する。生成されたメソッドこそ `encoding/json` が今呼ぶものなので、リファレンス側は odjson を一度もかけていない同一宣言の双子の型として同じ値を読む。そうすればリフレクションが期待どおりの答えを出す。v2 側の半分は `internal/testfixture/v2parity` が同じことをする。
- **[JSON Test Suite](https://seriot.ch/projects/parsing_json.html)**（318 ケース）を、ランタイムのスキャナに対しても *生成されたデコーダを通しても* 走らせる。各ケースは標準ライブラリが受け付けるものだけを受け付け、同じ値を出すことを要求される。
- **`encoding/json` のフィールド昇格ルール** を `go/types` の上に再実装し、3 つのケース全てに当たるよう組み立てた struct で `encoding/json` と突き合わせてテストする。
- **生成された出力はコミットされ、差分がチェックされる。** どれかのフィクスチャの出力を変えるジェネレータの変更は、ビルドを落とす。

パリティは `go.mod` のツールチェインに対して測っている。Go 1.27 以降 `encoding/json` は v1 互換モードで `encoding/json/v2` の上に実装されており、いくつかのエスケープ形式は古典的な v1 エンコーダと異なる — 正確な一覧は [`odjsonrt`](https://pkg.go.dev/github.com/mazrean/odjson/odjsonrt) のパッケージドキュメントを参照。
